## 一、必须先读的更正：上一轮方案的前提是错的

上一轮 `01_BUG-03方案修订.md` 的核心论断是「实时投影没有 `message.toolCallId`，所以**实时路径下所有工具结果都绑定失败**」。**本轮予以撤回。**

按 D5 要求实读真实网关 v0.10.3 与 App 源码后确认：

- App 聊天事件走 **DSH Host** 的 `/api/remote.mux`（`transport/index.ts:569`），端点 `session/follow` / `session/page`。
- 网关插件**不提供**这些端点（全文检索命中 0），它的扁平 `kind:'event'` 帧只发到审批旁路连接，而 `approvalGateway.handleFrame` **没有 `event` 分支**（只有 paired/hello/approval-requested/approval-resolved/approval-response 五种）。
- 全 `src/` 检索 `outputTruncated` / `buildWireEvent`：命中 0，**没有任何消费方**。
- 真实 Host 的 `tool/result` 用 `data.message.toolCallId`，**fold 本来就读它**；仓库自带样本里两条 call 与两条 result 的 ID 一一对应。

**所以「全部绑定失败」不成立。** 真实缺陷是另外几个，见 §三。完整证据与行号见 [01_D5协议核实.md](01_D5协议核实.md)。

> 这条更正直接来自第二方 D5「必须先验证」的要求。若按上一轮方案实施，会去修一个不存在的缺陷，并可能破坏本来正确的主路径。

## 三、实测确认的真实缺陷与修复

四个提交，每个都先用真实代码测出失败，再最小修复。

### 3.1 `a232ee0` 嵌套 content 的输出与失败判定

**缺陷（实测）**：真实 Host 的 content 是 `[{type:'tool-result', content:[{type:'text'}]}]`，而 `textOf` 只认**顶层** `type:'text'` → 取不到文本 → 落到 `asText` 的 `JSON.stringify` → **把整个 JSON 信封当成工具输出显示给用户**。`isError` 只看 `message.isError`，**漏掉嵌套块的 isError 与 `data.error`** → 失败显示成成功。

嵌套形状的依据是网关 v0.10.3 自己的遍历逻辑（`session-event-details.mjs` 的 `toolResultDetails`、`index.mjs:357-362` preview 循环、`:370` isError 三者取或）。

**修复**：新增 `toolResultText`（递归两种形状）与 `toolResultIsError`（口径与网关一致）。扁平与未知形状的回退**逐字保留**。

**证据**：`tool-result-fields-spec` 17 条，修前 **9 通过 / 8 失败** → 修后 **17 / 0**。其中 F5–F10 修前即绿，作为旧协议兼容基线。

### 3.2 `f016204` 显式 ID 匹配 + D1/D2

**缺陷（实测）**：
- 无 ID 结果的 `callId` 退化成 `''`，`find(x.callId === '')` 会认领**第一个**无 ID 块 → 到达顺序猜测（违反 D1）。
- `message.toolCallId='A'` 与 `source.callId='B'` 冲突时，`||` 优先级**静默选 A**（违反 D2）。
- 结果先到时建的占位块 `name='tool'`，真实调用到达后名字与参数**不回填**。

**修复**：`resolveCallId` 收集全部非空字符串来源，**一致才返回**；不一致返回 conflict，调用方**放弃绑定**并记诊断。占位块在真实调用到达时回填 name/input/rawArguments。

**证据**：`tool-result-binding-spec` 25 条，修前 **9 / 16** → 修后 **25 / 0**。

### 3.3 `8dedd2a` 结果未确认三态（D3 设计 B）

**缺陷（实测）**：`turn/end` 后缺失结果的工具 `pending` 永远为 true → ToolCard 永远「执行中」；WorkGroup `running` 永远 true；摘要把 3 个工具（2 个无结果）说成「**已执行 3 步**」，`failed=false` → **缺失结果被当成执行成功**。

**修复**：
- `ToolBlock` 新增 `resultUnconfirmed`，`turn/end` 时给仍 pending 的工具打上。
- 新增 `src/core/toolStatus.ts`，**ToolCard 与 WorkGroupCard 共用**一个四态判定（running / unconfirmed / failed / done），消除两处重复 ternary。
- WorkGroup 新增 `unconfirmedCount` / `executedCount`，摘要改为「已执行 1 步 · 2 步结果未确认」，**只把拿到结果的算已执行**。
- 组图标在有未确认时显示 `?` 而非 `✓`，无障碍标签同步。布局未改版。

**关键设计取舍**：**保留 `pending=true`**，只新增 `resultUnconfirmed`。因为 fold 的完成卡门禁（`completionStep`）依赖 `!b.pending` —— 若把未确认块的 pending 改成 false，门禁会放行，等于把缺失结果当成功。保留后门禁自然继续生效（U16 守住）。

**证据**：`tool-result-unconfirmed-spec` 18 条，修前 **8 / 10** → 修后 **18 / 0**。

### 3.4 `6c39687` 迟到恢复与诊断引用稳定性

**实测**：迟到结果的恢复、幂等、不倒退、跨轮迟到（含落在**已冻结前缀**里的轮次）在 3.3 之后**已全部正确**。唯一真实缺口是 `areTurnsStructurallyEqual` **不比较诊断数组** → 诊断变化的 turn 会复用过期对象。

**修复**：新增 `areUnattributedEqual` 并接入 turn 相等性判断。

**证据**：`tool-result-late-recovery-spec` 17 条，修前 **16 / 1** → 修后 **17 / 0**。

### 7.2 顺带暴露的既有门禁盲区

仓库本来有一条守卫「import .ts 的测试必须用 tsx 启动」（`runtime-compat-spec.mjs`），它**没有抓到**这个问题。实读发现其提取正则是：

```js
/node\s+(?:--require\s+\S+\s+)?(tests\/[\w.-]+\.mjs)/g
```

只认「`node` 紧跟单个测试文件」，**完全不认 `node --test a b c d` 分组**（`--test` 不在允许的前缀里，且只捕获第一个文件）。于是这一组 4 个文件**从未被扫描**。这是本轮之前就存在的盲区。
