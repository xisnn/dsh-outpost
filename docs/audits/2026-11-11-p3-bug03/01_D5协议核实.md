## 一、最重要的更正：上一轮审计的前提是错的

上一轮 `01_BUG-03方案修订.md` 断言：

> 「实时投影没有 `message`、没有 `toolCallId`……所以**实时路径下所有工具结果都绑定失败**」

**这个断言不成立，本轮予以撤回。** 它把网关插件的扁平线格式误当成了 fold 的输入。

### 1.1 聊天事件根本不走网关插件

| 事实 | 证据 |
|---|---|

| 网关插件**不提供**这些端点 | 在 `node_modules/dsh-plugin-mobile-gateway/lib/index.mjs` 全文检索 `remote.mux` / `session/follow` / `session/page`：**命中 0** |
| 网关的扁平 `kind:'event'` 帧只发到审批旁路连接 | `lib/index.mjs:3193-3219`，且 `:3216` 明确跳过 `sessionFollowerActive` 的客户端 |
| App 的旁路连接**不处理** `kind:'event'` | `src/core/approvalGateway.ts` 的 `handleFrame` 只有 5 个分支：`paired`(:965) / `hello`(:986) / `approval-requested`(:993) / `approval-resolved`(:1009) / `approval-response`(:1014)。**没有 `event` 分支** |
| App 里没有任何扁平字段的消费方 | 全 `src/` 检索 `outputTruncated`、`buildWireEvent`：**命中 0** |

**结论**：`buildWireEvent`（`lib/index.mjs:281-376`）产出的 `{kind:'event', event:{type, callId, preview, isError, output}}` 与 fold 无关。

### 1.2 fold 的真实输入形状

`EventRecord`（`src/core/types.ts:54-65`）：

```
{ type:'event', event:{ type, seq, time, data:{…} } }
```

`session/follow` 的增量帧由 `rpc/session.ts:202-212` 归一化：带 `event` 的原样透传，裸 `{type,seq,…}` 包一层。**两条路径（实时/历史）产出同一种形状**。

fold 入口 `foldEvents`（`fold/index.ts:263`）另有一层宽容解包 `r?.event ?? r`。

## 二、实时与历史的 content 形状

| 形状 | 来源 | fold 修前行为 |
|---|---|---|
| 扁平 `[{type:'text',text}]` | 仓库样本、`tests/fold-spec.mjs:83` | ✅ 正确提取 |
| 嵌套 `[{type:'tool-result', isError, content:[{type:'text',text}]}]` | 网关 v0.10.3 自身遍历逻辑：`lib/session-event-details.mjs` 的 `toolResultDetails`（`visit` 对 `tool-result` 递归 `content`）、`lib/index.mjs:357-362` 的 preview 循环、`:370` 的 isError 聚合 | ❌ 提取失败 |

修前 `textOf`（`fold/index.ts:169-176`）只认**顶层** `type==='text'`，嵌套形状取不到文本 → 落到 `asText`（`:227-235`）→ `JSON.stringify` → **把整个 JSON 信封当成工具输出显示**。

`isError` 修前只看 `message.isError === true`，**漏掉嵌套块上的 isError 与 `data.error`** —— 而网关自己的口径（`lib/index.mjs:370`）是三者取或。

## 三、D5 四个问题的实测答案

探针用真实 `foldEvents` / `foldEventsIncremental` 运行，原始输出见 ZIP 的 `probe-A-修前实测.txt`、`probe-B-D5重连乱序.txt`。

### 3.1 断线重连补历史能否恢复未绑定的结果？→ **能**

```
断线期间只有 call + turn/end : callId=A pending=true output=undefined
重连补历史拿到 result 后     : callId=A pending=false output="补回来的输出"
结论：补历史能否恢复未绑定结果 = true
```

机制：`store.ts` 按 seq 合并记录（`upsertStreamRecord:2306`），`rebuild:2372` 对全量记录重跑 fold；fold 是纯函数。**上一轮审计「重放不会自愈」的断言同样不能沿用**。

补历史入口共三处，形状一致：follow 首帧快照（`store.ts:2003-2009`）、重连补洞（`backfillReconnectGap:2088`）、向前翻页（`loadOlder:2267`）。

### 3.2 重复事件 → **幂等**

同一批事件重复传入，工具块数 1 / 1，`JSON.stringify` 完全相同。fold 按 seq 去重（`:265-273`）。

### 3.3 乱序 / 迟到 → **按 seq 排序后正确处理**

- 结果 seq=5 先于调用 seq=9：能绑定，但**工具名停留在占位 `'tool'`**（真实名 `read` 丢失）→ 本轮修复。
- `turn/end` 之后迟到结果：`pending=false`、output 正确填入 → 修前已能恢复，本轮补齐「未确认」态的恢复与不倒退测试。

### 3.4 跨 turn / 跨 step 归属

- **跨 turn 严格隔离**：turn1 与 turn2 用同一个 `callId='A'`，turn2 的结果只绑定 turn2，turn1 保持未决。✅ 修前已正确。
- **跨 step**：结果带 `step=2` 但 `toolCallId` 指向 step1 的调用时，fold 在**整个 turn 的所有 step**里按 ID 查找（`:474-476`），绑定到调用真实所在的 step1。

> **这不是缺陷，不要"修"它。** `tool/result` 的 `step` 字段不是定位调用的权威依据，`callId` 才是。按 ID 找到真实调用所在 step 是正确行为；若强行按 `step` 限制查找范围，反而会让合法结果绑不上。本轮用 B17 把这个行为固定下来。

## 四、实测确认的真实缺陷（本轮修复范围）

| 编号 | 缺陷 | 修前实测 |
|---|---|---|
| R1 | 嵌套 content 输出提取失败 | output 是 JSON 信封字符串，不是 `真实工具输出文本` |
| R7 | 嵌套块 isError 被忽略 | `message.isError` 缺失时判为 `false`（失败显示成成功） |
| R2 | 缺失结果永远「执行中」 | `turn/end` 后 `pending=true`，ToolCard 显示「执行中」，不收敛 |

| R4 | 无 ID 结果按顺序认领 | 两个无 ID 调用，结果绑到**第一个**（`read`），违反 D1 |
| R6 | 冲突 ID 按优先级静默选择 | `message.toolCallId='A'` 与 `source.callId='B'` 冲突 → 静默绑 A，违反 D2 |
| D5-a | 占位块工具名/参数不回填 | 结果先到时建块 `name='tool'`，真实调用到达后仍是 `tool` |
