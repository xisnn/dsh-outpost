## 一、BUG-02：`DshConnection.call()` 响应体永久挂起

### 1.1 已核实的当前代码事实

`dsh-mobile/src/core/transport/index.ts`：

| 位置 | 事实 |
|---|---|
| `:360` | `async call<T>(endpoint, args)` |
| `:365-366` | `timeoutMs` 来自 `args.__timeoutMs` 覆盖，否则 `RPC_TIMEOUT_MS` |
| `:378-379` | `const ctrl = new AbortController(); const timer = setTimeout(() => ctrl.abort(), timeoutMs)` |
| `:396` | `signal: ctrl.signal` 已传给 fetch ✅ |
| **`:398`** | **`clearTimeout(timer)` —— 收到响应头就撤销定时器** |
| **`:400`** | **`clearTimeout(timer)` —— fetch 抛错路径** |
| `:417-420` | `if (!res.ok) throw makeRpcError(..., 'http', ...)` |
| `:422-435` | Set-Cookie 轮换（含动态 import） |
| **`:440`** | **`parsed = (await res.json())` —— 此时已无定时器保护** |
| `:441-443` | `catch { parsed = undefined }` —— **吞掉所有异常** |
| `:445-448` | `if (!result) throw makeRpcError(..., 'malformed', ...)` |

对照组 `request()`（`:468`）：timer `:482`，`await res.text()` `:523`，**`clearTimeout` 在 `:537` 的 `finally`** —— 覆盖整个响应体读取。

**结论**：`call()` 与 `request()` 的定时器生命周期不一致。服务端返回 200 响应头后卡住响应体时，`call()` 的 Promise **永久挂起**。

**影响面**（已核实调用点）：`call()` 承载 `session/prompt`（`__timeoutMs: 180_000`）、`session/page`（60s）、`session/list`。挂起会导致 `runPendingSend` 到不了终态、记录停在 `sending`（不进 `unknown`，用户重启前无恢复手段）、`ChatScreen` 的 `finally` 永不执行（发送按钮死掉、spinner 永转）、`loadOlder` 的 `loadingOlder` 永不清除。

### 1.2 本轮新增发现 —— 只移 `clearTimeout` 是不够的

审计建议是「把 `clearTimeout(timer)` 移进包裹整个响应体读取的 `finally`」。**本轮核实发现该建议单独实施会引入一个语义回归：**

`:441` 的 `catch { parsed = undefined }` 会吞掉**所有**异常，包括 abort。所以定时器修好之后，响应体阶段超时的实际路径是：

```
timer 触发 → ctrl.abort() → res.json() reject(AbortError)
→ :441 catch 吞掉 → parsed = undefined
→ :445 !result → 抛「malformed response（没有 result 字段）」
```

用户看到的是**「返回格式不对」**，而真实原因是**「超时」**。这两者的可操作建议完全不同（等一下再试 vs 怀疑上游改接口），且 `:405-411` 已经为 fetch 阶段建立了「超时单独提示」的既有约定，响应体阶段却会破坏它。

**因此 BUG-02 的修复必须包含两部分**，缺一不可：
- (a) 定时器覆盖到响应体读完；
- (b) 响应体的 catch 里判别 abort，超时走 `请求超时` 而不是 `malformed`。

### 1.3 另一个本轮新增发现 —— 现有测试会阻碍正确修复

`tests/timeout-throttle-spec.mjs:72-77`（已核实原文）：

```js
check('call() 在成功/失败路径都 clearTimeout', () => {
  const i = transportSrc.indexOf('async call<T');
  const body = transportSrc.slice(i, i + 3500);
  const count = (body.match(/clearTimeout\(timer\)/g) || []).length;
  return count >= 2 ? true : `只清了 ${count} 处，有路径会泄漏定时器`;
});
```

正确的单一 `finally` 修复会让 `count` 变成 **1** → 这条检查失败。**它统计出现次数，而不是验证「每条退出路径都清了定时器」**，属于把实现细节当契约。

而且（已用真实执行日志核实）：`timeout-throttle-spec.mjs` 与 `throttle-behavior-spec.mjs` 只挂在 `test:perf` 下，**不在 `test` / `test:integration` / `test:node20` 任何一条链中**，本地与 CI 全量日志中出现次数均为 **0**。所以这个冲突不会在 CI 上暴露，只会在有人跑 `npm run test:perf` 时突然出现。

> 纠正一条审计旧结论：`transport-request-spec.mjs` **在 CI 中**（`[70/107]`，本地与 CI 均 PASS）。此前「不在 CI」的判断源于误读 `--dry-run` 输出（它只打印顶层命令，不展开叶子）。

**步骤 2 —— 最小修复**

形状（示意，实施时以实际代码为准）：

```ts
const ctrl = new AbortController();
const timer = setTimeout(() => ctrl.abort(), timeoutMs);
try {
  let res: Response;
  try {
    res = await this.fetchImpl(url, { ... signal: ctrl.signal });
  } catch (e) {
    // 既有错误映射逐字保留（AbortError → 请求超时；其它 → network）
    // 只删掉这里的 clearTimeout —— 由外层 finally 统一负责
  }
  if (!res.ok) throw makeRpcError(endpoint, 'http', `HTTP ${res.status}`);
  // Set-Cookie 轮换块逐字保留
  let parsed;
  try {
    parsed = await res.json();
  } catch (e) {
    // 【新增】abort 判别：响应体阶段超时也要说「超时」
    if (ctrl.signal.aborted || (e as { name?: string })?.name === 'AbortError') {
      throw makeRpcError(endpoint, 'network',
        `请求超时（${Math.round(timeoutMs / 1000)} 秒无响应）`, e);
    }
    parsed = undefined;   // 其它解析失败仍走 malformed，既有语义不变
  }
  // 其余 result 校验逐字保留
  return result.value as T;
} finally {
  clearTimeout(timer);
}
```

要点：
- 删除 `:398` 与 `:400` 两处 `clearTimeout`，收敛为**单一 `finally`**，与 `request()` 对齐
- `finally` 必须覆盖 `!res.ok` 抛错、Set-Cookie 轮换、响应体读取、result 校验**全部**退出路径
- 正常路径**零行为变化**：唯一差异是「慢响应体现在会在 `timeoutMs` 处 abort 而非永久挂起」——这正是意图
- 不改 `timeoutMs` 默认值、不改 `__timeoutMs` 摘除逻辑、不改错误分类枚举

### 2.2 三条故障链（均已核实）

**链 A —— id 拼写不对称导致结果被丢弃或错误覆写**

结果只带 `callId` / `id`（不带 `toolCallId`）时，`:469-471` 解析出 `''`：
- 若没有块的 `callId === ''` → `target` 为 `undefined`，`else if (callId)` 为假 → **结果被静默丢弃**，原块 `pending` 永为 `true`
- 若确有块的 `callId === ''` → `find` 返回**第一个**（无守卫）→ N 个结果全部覆写 1 号块，2..N 号块永久 `pending`

同一个 `''` 还会**在上游禁用去重**（`:407-409` / `:441-443` 都是 `callId ? find : undefined`）：一个无 id 的 `assistant/message` tool-call 加一个无 id 的 `tool/call` 会产出**两个块** —— 即历史上修过的「重复工具调用块」回归。

**链 B —— `turn/end` 从不收尾 pending**：轮次结束了，卡住的工具块仍 `pending=true`。

**链 C —— 权威恢复也不收尾**：`applyAuthoritativeRunningOverride` 只改轮次级 `running`。

**共同后果**：`:652` 只要发现任一 `pending` 工具块就**永久压制完成卡**，并在 `reason:'completed'` 的轮次里留下永久 spinner。fold 对已持久化事件是确定性的，所以**重连 / 重放不会自愈**。

触发场景（任一）：链 A 的 id 缺失；`backfillReconnectGap`（`store.ts:2088-2127`）的安全上限放弃补洞；WS 中断 / 轮次中止发生在 tool-call 之后；服务端对被取消的工具从不发 `tool/result`。

### 2.3 已核实的安全前提 —— 标记 `isError=true` 不会触发重发

这是「不得把缺失结果当成功」与「不得自动重试」两条要求能同时满足的关键，本轮已逐点核实：

`block.isError` 的**全部**消费点：

| 位置 | 用途 |
|---|---|
| `ToolCard.tsx:154,157,162,231` | 纯展示（配色、文案、卡片边框、输出预览配色） |
| `WorkGroupCard.tsx:46` | 纯展示（`执行中 / 失败 / 完成` 三态文案） |
| `workGroup.ts:114` | `const failed = toolBlocks.some(b => b.isError)` → 只写入纯视图对象 `WorkGroupView` |

（其余 `isError` 命中是无关的局部变量：`ConnectionBanner.tsx:28`、`picker.ts` 的 `isErrorWithCode`。）

- `grep -rniE 'retry|resend|requeue'` 在 `workGroup.ts` 与 `WorkGroupCard.tsx` 中 **零命中**（已实测）
- `store.ts` 中的 `retry` 命中是 `retryTimer` / `retryAttempt`，属 **stream 重连**；持久化发件箱的 `pendingSends.retry(requestId)` 以 `requestId` 为键，**与工具块无任何耦合**

**结论**：把未收到结果的块标记为 `isError=true` 只会改变展示，不会产生任何出站请求。

```

isError = true                                   // 渲染为「失败」+ danger 配色 = 异常终止语义
output ??= '（未收到工具结果，轮次已结束）'        // 明确是未知，不是空成功
```

三者**缺一不可**。理由已核实：`:652` 只看 `pending`，所以必须清 `pending` 才能解除压制；`ToolCard:152-157` 以成功为默认分支，所以只清 `pending` 会渲染成「完成」+ success 配色。

**禁止的写法**（明确记录，防止实施走偏）：
- ❌ 只清 `pending` 而不设 `isError` → 从未收到结果的工具被显示为**成功执行**
- ❌ 把 `output` 留空 → 空 output + `isError=false` 看起来像成功的空结果
- ❌ 在 `turn/end` 里补发任何请求或重放事件 → 违反「不得自动重试」
- ❌ 用 `pending=false` + 自定义「未知」状态字段 → `ToolCard` 不认这个字段，仍会落到成功分支；除非同时改渲染层，但那超出最小修复范围

理由：
1. BUG-02 风险更低（`finally` + 一个 abort 判别），且修复面窄，先做能建立节奏；
2. BUG-02 的前置工作包含「把 `test:perf` 接入 CI」，这会**增强后续所有改动的护栏**，对 BUG-03 有利；
3. BUG-03 会改变可见 UI 语义，需要更多复核时间，放在后面便于第二方集中审。
