## 三、阶段三：失败定位与修复

```

```

失败断言（2 条，均在 §7）：

```

      Cannot bind argument to parameter 'Path' because it is null.
FAIL  -Status 真实执行：输出原有文案
```

同节其余断言全部 OK，包括「-Status 真实执行：没有触发门禁拒绝」与全部分支顺序断言。

### 3.2 根因

`start-tunnel.ps1:74`（cloudflared 探测的回退分支）：

```powershell
$tries = @(
    'E:\cloudflared\cloudflared.exe',
    (Join-Path $env:LOCALAPPDATA 'cloudflared\cloudflared.exe'),   # ← :74
    (Join-Path $env:ProgramFiles 'cloudflared\cloudflared.exe')
)
```

ubuntu runner 上 `LOCALAPPDATA` / `ProgramFiles` **不存在** → `Join-Path` 收到 `$null` → 抛 `ParameterArgumentValidationErrorNullNotAllowed`。脚本 `$ErrorActionPreference='Stop'`，于是在**走到 `-Status` 分支之前**就 exit 1。

测试把这个 exit 1 误读成「门禁拦住了只读命令」，而它断言的恰恰是相反的行为。

**分类：测试可移植性问题。** 不是生产代码缺陷（`start-tunnel.ps1` 是 Windows 专用脚本，依赖 `%LOCALAPPDATA%` 是合理的），不是门禁失效，不是环境问题需要改 CI 镜像。

### 3.3 修复 1 —— `7b95af5`（+8 行，1 个测试文件）

在 §7 的 spawn 环境里，**仅当缺失时**补上这两个变量指向临时目录：

```js
LOCALAPPDATA: process.env.LOCALAPPDATA || tmp,
ProgramFiles: process.env.ProgramFiles || tmp,
```

Windows 沿用原值 → 本地行为完全不变。未改任何生产代码，未削弱门禁，未跳过任何测试。

## 四、本轮新发现（未修复，移交后续）

以下 2 项不是本轮 CI 失败原因，按「仅修复本阶段直接相关的问题」原则**未在本轮改动**，如实记录并给出建议。

### 4.1 `gateway-startup-gate-spec.mjs:239-244` 存在恒真断言

```js
if (code !== 0) {
  check(true, '补丁未应用时 apply.mjs --check 返回非 0');
  check(/认证|补丁|apply\.mjs/.test(out) || out.length > 0, 'apply.mjs 给出可读输出');
} else {
  check(true, '补丁已应用时 apply.mjs --check 返回 0');
}
```

两个 `check(true, ...)` **永远不会失败**——它们只是给观察结果贴标签，没有断言 `code` 的值。第二条的 `|| out.length > 0` 也几乎恒真。

这解释了本轮观察到的一个现象：该 spec 在本地是 **54 条**、在 CI 是 **55 条**——因为分支取决于运行环境的真实补丁状态（本机插件已打补丁走 else，CI fixture 未打补丁走 if）。两边都「通过」，但两边都有一条断言是空的，且**同一次运行只覆盖一个分支**。

这与 P2 修过的 `f38d9e2`（契约测试零断言假绿）属同一类问题。建议后续改为真实断言 `code !== 0` / `code === 0`，并用 fixture 让两个分支在同一次运行中都被覆盖。

### 4.2 `test:perf` 是孤儿脚本，其中的测试会阻碍 BUG-02 的正确修复

`timeout-throttle-spec.mjs` 与 `throttle-behavior-spec.mjs` 只挂在 `test:perf` 下，**不在 `test` / `test:integration` / `test:node20` 任何一条链中**。实测：本地与 CI 全量日志中出现次数均为 **0**。

而 `timeout-throttle-spec.mjs:72-77` 要求：

```js
const count = (body.match(/clearTimeout\(timer\)/g) || []).length;
return count >= 2 ? true : `只清了 ${count} 处，有路径会泄漏定时器`;
```

BUG-02 的正确修复是把 `clearTimeout` 收敛到**单一 `finally`**，那会让 count 变成 1 → 该测试失败。**现有测试 actively 阻碍正确修复**，且因为它不在 CI 中，这个冲突不会在 CI 上暴露，只会在有人跑 `npm run test:perf` 时突然出现。
