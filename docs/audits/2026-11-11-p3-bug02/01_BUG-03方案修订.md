## 一、本轮新增的决定性证据

### 1.1 协议对 `callId` 的规定是明确的

`dsh-mobile/node_modules/dsh-plugin-mobile-gateway/PROTOCOL.md:1129-1131`（插件版本 **0.10.3**）：

```
- tool/call   → {turn, step, callId, name, arguments}
- tool/result → {turn, step, callId, isError, preview(≤400字符), output, outputTruncated, error?}
```

**两者的规范字段都是 `callId`，都在 `data` 顶层，都带 `turn` 与 `step`。**
每个 `event` 帧根节点还带持久 `seq`（`PROTOCOL.md:1119-1122`），历史与实时按 `sessionId + seq` 合并（`:776`）。

### 1.2 实时路径与历史路径的**形状不同** —— 这是原方案漏掉的关键

网关 `lib/index.mjs` 有两条独立路径：

**实时推送**（`buildWireEvent` @ `:281`，被 `:2949` 的 session follower 与 `:3196` 的 `session/event` 广播调用）对 `tool/result` 做**投影**（`:355-377`）：

```js
event: {
  type: 'tool/result',
  turn: d.turn,
  step: d.step,
  callId: d.message?.toolCallId ?? d.message?.source?.callId,   // ← :369
  isError: d.message?.isError === true || !!d.error || …,
  preview,
  ...toolResultDetails(d),        // 只返回 { output, outputTruncated }
  ...(d.error ? { error: d.error } : {}),
}
```

`toolResultDetails` 定义在 `lib/session-event-details.mjs:28-42`，**只返回 `{output, outputTruncated}`**（已逐行核实）。

所以实时 `tool/result` 的 `data` 键**恰好**是：
`{type, turn, step, callId, isError, preview, output, outputTruncated, error?}`
—— **没有 `message`，没有 `toolCallId`**。

**历史路径**（`lib/index.mjs:1143-1160`）保留**原始形状**：`return { ...event, data: { ...d, ...details, … } }`，因此 `d.message` 存在，`message.toolCallId` 可用。

### 1.3 由此得出的缺陷范围 —— 比审计描述的更严重

当前 `fold/index.ts:465-471`：

```ts
const message = (d.message ?? {}) as Record<string, unknown>;
const callId =
  (typeof message.toolCallId === 'string' && message.toolCallId) ||
  (typeof d.toolCallId === 'string' ? d.toolCallId : '');
```

对照两条路径：

| 路径 | `d.message.toolCallId` | `d.toolCallId` | 解析结果 |
|---|---|---|---|
| 历史 | ✅ 存在 | ✗ | 正确绑定 |
| **实时** | ✗（无 `message`） | ✗（键名是 `callId`） | **`''` → 结果被丢弃** |

**也就是说：实时路径下 `tool/result` 的规范字段 `d.callId` 根本没被读取，所有实时工具结果都绑定失败**，不只是「无 ID 的边缘情况」。审计把它描述为「3 种拼写 vs 2 种拼写的不对称」，低估了范围。

同一段代码还有两处同源问题（均已核实）：

- `:478` `const output = textOf(message.content) || asText(message.content)` —— 实时路径无 `message`，**output 恒为空**；规范字段 `d.output` / `d.preview` **没有任何回退**（`grep -n 'd.output\|d.preview' src/core/fold/index.ts` 零命中）。
- `:481` `target.isError = message.isError === true` —— 实时路径恒为 `false`；规范字段是 `d.isError`。

> **对审计一处结论的保留意见**：审计称「fold 对已持久化事件是确定性的，所以重连/重放不会自愈」。本轮发现实时与历史形状不同，而 `store.ts` 中**找不到本地事件持久化**（`grep persistEvents|saveEvents|replayEvents|loadEvents` 零命中），重连走 `backfillReconnectGap`（`:2088`）向网关补历史。若补回的是**历史形状**，则 `message.toolCallId` 存在、**会**绑定成功，即可能自愈。**这一点必须在实施时用测试确认，不能直接沿用审计原文。** 本修订不把它当作已知事实。

### 1.4 协议**没有**给出工具结果的顺序保证

对 `PROTOCOL.md` 全文检索 `并行 / 并发 / parallel / concurren / 乱序 / 顺序 / out-of-order`：

- 命中的都是**别的**语义：配对 endpoints 合并顺序（`:105`）、问题批次 answers 顺序（`:268`）、菜单分组顺序（`:461`）、附件并发下载限制（`:758`）、日程并发冲突（`:1222`）、转写并发名额（`:1360`）。
- **没有任何一条**声明 `tool/result` 与 `tool/call` 的到达顺序一致，也没有声明同一 `step` 内多个工具是串行还是并行。

**结论：协议层面不存在可用于顺序绑定的保证。**

## 二、修正 2：禁止对多个无 ID 工具调用做顺序绑定

### 2.1 原方案的错误

原方案 §2.4 步骤 3 写的是：

> 当解析出的 `callId === ''` 时，只匹配仍处于 `pending && output === undefined` 的块，绝不盲取首个。

**这仍然是顺序绑定**：「第一个尚未 settle 的块」就是按到达顺序猜归属。在协议没有顺序保证、且同一 step 内可能有多个工具的前提下，这会把 A 工具的输出写到 B 工具的卡片上 —— **比丢弃更糟**，因为它伪造了一个看似正确的归属。第二方的反对成立，撤回该设计。

### 2.2 修订后的绑定策略（按证据强度分级）

**第 1 级 —— 显式 ID 匹配（唯一允许的自动绑定）**
解析出非空 `callId` 时，按 ID 精确匹配。这是协议保证的关联方式。

**第 2 级 —— 结构坐标收窄（只用于排除，不用于认定）**
`turn` + `step` 可以把候选集缩小到同一轮同一步，但**不能**据此认定归属：同一 step 内可能有多个工具。坐标只用于「候选是否唯一」的判断，不用于排序挑选。

**第 3 级 —— 无法可靠匹配 → 保留未确认语义**
当 `callId` 为空（或候选不唯一）时：

- **不得**写入任何既有工具块的 `output` / `isError` / `pending`；
- 该结果作为**独立的「未归属结果」条目**保留下来（携带 `turn` / `step` / `seq` / `output` / `isError`），以便诊断与后续人工/协议改进；
- 原工具块**保持未确认**，由 §四 的 `turn/end` 收尾统一处理为「未收到结果」，**绝不**显示为成功。

**唯一例外（可证明安全的窄情形）**：若同一 `turn` + `step` 内**恰好只有一个** `pending` 工具块，且**恰好只有一条**无 ID 结果，则归属是**可证明唯一的**，可以绑定。这不是顺序猜测，而是基数为 1 的排除法。

> 该例外是否纳入本轮，列为**待决策项 D1**（见 §七）。保守做法是先不纳入：先只修「实时路径读不到 `d.callId`」这个确定缺陷，无 ID 情形一律保留未确认。这样即使例外判断有误也不会错误归属。**建议先不纳入。**

### 2.3 为什么「保留未确认」优于「尽力猜」

- 猜错 → 用户看到 A 工具的输出挂在 B 工具下，且状态是「完成」，**无从察觉错误**。
- 保留未确认 → 用户看到「未收到结果」，知道信息缺失，可以重查历史。

在审批/设备控制链上（P1 的 `PhoneTools` 等），错误归属的工具输出还可能误导用户对「做了什么」的判断。宁可缺失，不可伪造。

## 三、修正 3：`tool/result` 字段优先级方案 + 冲突负向测试

### 3.1 原方案的问题

原方案只说「补上与 `:402-406` / `:434-438` 完全相同的回退链」，即：

```
message.callId → message.id → message.toolCallId → d.callId → d.id → d.toolCallId → ''
```

两个问题：
1. **把 `message.*` 排在 `d.callId` 前面**，而协议规范字段是 `d.callId`。当两者共存且冲突时，会优先采信非规范来源。
2. **完全没有定义「多字段共存且值冲突」时的行为**，也没有对应测试。

### 3.2 修订后的优先级（按协议权威性排序）

依据 §1.1/§1.2 的实际来源：

| 优先级 | 字段 | 依据 |
|---|---|---|
| 1 | `d.callId` | **协议规范字段**（`PROTOCOL.md:1131`），实时路径唯一来源 |
| 2 | `d.message.toolCallId` | 历史路径的原始上游字段（网关 `:369` 的第一来源） |
| 3 | `d.message.source.callId` | 网关 `:369` 的第二来源（`??` 右侧） |
| 4 | `d.toolCallId` | 既有代码已支持的旧拼写，**保留以兼容旧协议** |
| 5 | `d.id` / `d.message.callId` / `d.message.id` | 与 `tool/call` 侧对齐的兜底拼写 |

**规则**：
- 取**第一个非空字符串**，后续字段不再参与。
- **只接受非空字符串**；`''`、`null`、`undefined`、数字、对象一律视为缺失（避免 `0`、`false` 被当成有效 ID）。
- **保护旧协议行为**：优先级 4 的 `d.toolCallId` 必须保留，且当只有它存在时结果与修复前**逐字一致**。

### 3.3 冲突的处理 —— 必须显式定义，不能静默

当多个字段共存且值**不同**时：

- **采用优先级最高者**（规则确定、可测试）；
- 但**必须记录冲突**（例如在块上留一个诊断标记，或计入一个可断言的冲突计数），因为冲突意味着上游形状异常，静默采信会掩盖问题；
- **绝不**因为冲突就丢弃结果或随机挑选。

> 冲突是否要影响绑定（例如冲突时降级为「未确认」）列为**待决策项 D2**。建议：**仍按优先级绑定，但记录冲突**。理由是丢弃会让正常但形状冗余的事件失去结果，代价更大；而记录足以暴露问题。

### 3.4 必须新增的负向测试（冲突与类型）

| # | 场景 | 断言 |
|---|---|---|
| C1 | `d.callId='A'` 且 `d.message.toolCallId='B'` | 绑定到 **A**（规范字段优先），并记录冲突 |
| C2 | `d.callId='A'` 且 `d.toolCallId='B'` | 绑定到 **A**，记录冲突 |
| C3 | `d.message.toolCallId='A'` 且 `d.message.source.callId='B'` | 绑定到 **A**（网关 `??` 的左侧优先），记录冲突 |
| C4 | 只有 `d.toolCallId='A'`（旧协议） | 绑定到 A，且结果与修复前**逐字一致** |
| C5 | 只有 `d.message.toolCallId='A'`（历史形状） | 绑定到 A，行为不变 |
| C6 | 只有 `d.callId='A'`（实时形状） | **绑定到 A** —— 这是修复前失败的主场景 |
| C7 | `d.callId=''` 且 `d.toolCallId='A'` | 空串不算有效，回退到 A |
| C8 | `d.callId=0` / `false` / `null` / `{}` / `[]` | 一律视为缺失，**不得**被当成 ID（防止 `0`、`false` 被字符串化后误匹配） |
| C9 | 所有 ID 字段都缺失 | 走 §二 第 3 级：保留未确认，**不得**写入任何既有块 |
| C10 | 两个无 ID 结果 + 两个无 ID 调用 | **不得**发生顺序绑定；两个块都保持未确认，两条结果都作为未归属条目保留 |
| C11 | 冲突字段值相同（`d.callId='A'` 且 `d.toolCallId='A'`） | 正常绑定，**不**记为冲突 |

C1–C3、C6–C10 在修复前必须失败；C4、C5、C11 在修复前必须通过（旧协议保护）。

## 四、修正 4：`turn/end` 收尾必须区分「已确认失败」与「未收到结果」

### 4.1 协议提供的终态信息

`PROTOCOL.md:1132`：`turn/start|end` → `{turn, step, reason?, reasonDetails?}`，`reasonDetails` 提供**结构化终态错误或取消来源**。
`PROTOCOL.md:1136`：**最终错误以 `turn/end.reason: "error"` 为准，`aborted` 显示取消，`interrupted` 显示中断。**

同段还有一条对本设计很关键的警告：

> Shell 的非零退出码可能仅在输出末尾 `[exit code: N]` 中，Host 的 `isError` 仍为 false；展示时可以标记该工具失败，但不能据此终止整轮。

即 **`isError` 不是工具失败的唯一信号**，但反过来「收到了结果且 `isError=false`」应视为**已确认完成**（除非另有证据）。

### 4.2 三种语义必须可区分

| 语义 | 判定依据 | 期望展示 |
|---|---|---|
| **已确认完成** | 收到 `tool/result`，`isError=false` | 完成（success） |
| **已确认失败** | 收到 `tool/result`，`isError=true` 或带 `error` | 失败（danger）+ **真实错误输出** |
| **未收到结果** | 直到 `turn/end` 都没有匹配的 `tool/result` | **不得是成功**；需与「已确认失败」可区分 |

原方案把第三种直接设成 `isError=true`，会与第二种**混为一谈** —— 用户无法区分「工具真的跑失败了」和「我们没收到它的结果」。第二方要求区分，成立。

### 4.3 两个候选设计（需决策 D3）

**设计 A（最小改动，信息层区分）**
`turn/end` 时对未收到结果的块设 `pending=false`、`isError=true`、`output ??= '（未收到工具结果，轮次已结束）'`。
- 状态标签仍是「失败」，但**正文文案**明确说明是结果缺失，与真实错误输出可区分。
- 只改 fold，不动渲染层。
- 缺点：状态标签与配色和「已确认失败」相同，快速扫视时无法区分。

**设计 B（渲染层三态，语义完全区分）**
在 `ToolBlock` 上新增一个明确标记（如 `resultMissing: true`），`ToolCard` / `WorkGroupCard` 增加第四种状态文案（如「未收到结果」）与独立配色。
- 优点：语义彻底区分，符合「不得把缺失展示为成功」的最强解读。
- 缺点：触及渲染层与 `workGroup.ts:114` 的 `failed` 聚合，改动面更大，需要额外的 UI 回归；且 `WorkGroupView` 是纯视图对象，要一并扩展。

**建议：设计 B**，因为第二方明确要求「区分」，而 A 只在正文里区分、状态标签仍混淆。但 B 的改动面更大，**必须由第二方确认后再实施**。若选 B，需同时定义 `workGroup.ts:114` 的 `failed` 是否把「未收到结果」计入（建议计入，但文案区分）。

### 4.4 迟到 `tool/result` 的恢复（必须可恢复，不能一次性定死）

`turn/end` 的收尾**不是终局判决**。协议允许事件乱序/跨页/重复（`fold/index.ts:5` 注释已明确），且重连补洞可能把迟到的结果送回来。因此：

- 收尾标记必须是**可被后续真实结果覆盖**的；
- 迟到的 `tool/result` 若能按 ID 匹配到该块，必须：
  - 用真实 `output` 覆盖占位文案；
  - 用真实 `isError` 覆盖收尾时的推断；
  - 清除「未收到结果」标记；
  - `pending` 保持 `false`（已经结束了，不要重新转圈）。
- **幂等**：同一条迟到结果重复到达，结果一致（fold 已按 `seq` 去重，`:269-271`）。
- **不得倒退**：已确认完成/失败的块，不能被后到的收尾逻辑改回「未收到结果」。

必须新增的恢复测试：

| # | 场景 | 断言 |
|---|---|---|
| L1 | `tool/call` → `turn/end(completed)` → 迟到 `tool/result(isError=false)` | 块变为**完成**，占位文案被真实 output 覆盖，未收到标记被清除，`pending=false` |
| L2 | 同上但迟到结果 `isError=true` | 块变为**已确认失败**，output 为真实错误内容 |
| L3 | L1 之后再重复同一条结果（同 seq） | 结果不变（幂等） |
| L4 | `turn/end` 收尾后，再来一条**无 ID** 结果 | **不得**覆盖已收尾块（走未归属条目），除非 §2.2 例外被采纳且可证明唯一 |
| L5 | 已收到结果的块，随后 `turn/end` | **不得**被改成「未收到结果」，output/isError 逐字不变 |
| L6 | `turn/end reason=error` / `aborted` / `interrupted` | 未收到结果的块都不得显示成功；三种 reason 下的文案/语义符合 §4.1 |
| L7 | 迟到结果带 `turn`/`step` 与块不一致 | 不得跨轮错误归属 |

### 4.5 禁止的写法（沿用并强化）

- ❌ 只清 `pending` 不设任何失败/缺失标记 → 渲染成「完成」+ success（`ToolCard.tsx:152-157` 以成功为默认分支，已核实）
- ❌ `output` 留空 → 空 output + 非失败 = 看起来像成功的空结果
- ❌ 把「未收到结果」与「已确认失败」用完全相同的状态与文案表示（修正 4 明确禁止）
- ❌ 在 `turn/end` 里补发请求或重放事件 → 违反「不得自动重试」
- ❌ 收尾后拒绝接受迟到的真实结果 → 违反可恢复性要求
