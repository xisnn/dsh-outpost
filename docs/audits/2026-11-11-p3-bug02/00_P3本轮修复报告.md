## 二、BUG-02 实施

### 2.1 缺陷（已在当前代码核实）

`dsh-mobile/src/core/transport/index.ts`：

| 位置 | 修前事实 |
|---|---|
| `:379` | `const timer = setTimeout(() => ctrl.abort(), timeoutMs)` |
| **`:398` / `:400`** | **收到响应头 / fetch 抛错时就 `clearTimeout(timer)`** |
| **`:440`** | **`parsed = (await res.json())` —— 此时已无定时器保护** |
| `:441-443` | `catch { parsed = undefined }` —— 吞掉所有异常 |
| 对照 `request()` | timer `:482`，`await res.text()` `:523`，**`clearTimeout` 在 `:537` 的 `finally`** |

服务端回 200 头后卡住响应体 → `call()` 的 Promise **永久挂起**。影响 `session/prompt`（`__timeoutMs: 180_000`，`rpc/session.ts:117`）、`session/page`（60s）、`session/list`。

### 2.2 修复内容

**生产代码只改 1 个文件**：`transport/index.ts`，`+91/−70`；**忽略空白后 `+24/−3`**，其中 11 行是注释。真实语义改动只有三处：

1. 删除 `:398` 与 `:400` 两处 `clearTimeout(timer)`
2. 用**单一 `try/finally`** 包住从 fetch 到 `return result.value` 的全部退出路径，`finally` 里 `clearTimeout(timer)` —— 与 `request()` 对齐
3. 响应体的 catch 里**判别 abort**：`ctrl.signal.aborted || e?.name === 'AbortError'` → 抛「请求超时」，而不是落到 `malformed`

**第 3 点是原方案漏掉的**：只移定时器的话，abort 会被 `:441` 的 catch 吞掉 → `parsed=undefined` → `:447` 抛「malformed response（没有 result 字段）」，把**超时**说成**上游改了返回格式**。两者的用户可操作建议完全不同，也破坏了 fetch 阶段已建立的「超时单独提示」约定。

正常路径**零行为变化**：唯一差异是慢响应体现在会在 `timeoutMs` 处 abort 而非永久挂起。

### 2.3 测试（按修正 1 与修正 6）

**A. transport 层（`transport-request-spec.mjs`，+218 行）**

该文件原本 **32 条断言全部是 `request()`，`call()` 覆盖为零**（已核实）。新增：

| 用例 | 守什么 |
|---|---|
| B2 | 响应体卡死时**必须在有限时间内结束**（200ms 内 settle，超时设 30ms） |
| B1 | 响应体阶段超时抛 `/请求超时/` |
| B3 | 超时**不得**被误报成 `malformed` |
| B4 | 正常快速响应返回值不变 |
| B5 | HTTP 403 仍抛 `HTTP 403`，**且定时器被清理** |
| B6 | json 抛非 abort 异常仍走 `malformed`，定时器被清理 |
| B7 | `result.ok===false` 仍抛 rpc 错误，定时器被清理 |
| B8 | Set-Cookie 轮换仍生效，定时器被清理 |
| B9 | fetch 阶段超时的既有行为不变 |

B5–B8 用 `trackTimers()` 直接观测真实定时器的创建/清理，断言 `leaked()===0` —— 这是「每条退出路径都清定时器」的**行为证据**，不是数源码出现次数。

**B. store 层（`pending-send-send-flow-spec.mjs`，+139 行）—— 修正 1 要求的三项**

关键设计：**不 stub `store.api.prompt`**。原 harness 会给它挂 own property 桩，那会绕过真实 transport、测不到 BUG-02。新 harness `delete h.store.api.prompt` 恢复 `SessionApi.prototype.prompt`，注入「200 头已回、body 永久卡死」的 `fetchImpl`，让 `call('session/prompt')` → 超时 → abort → 抛错 → store 落 unknown 整条链真跑。

`session/prompt` 的 `__timeoutMs` 硬编码 180s，测试用 `withShortRpcTimeouts` **只把 ≥60s 的定时器缩短**，不动重连退避/节流等其它定时器，因此仍走真实代码路径，未改产品常量。

| 用例 | 断言 |
|---|---|
| **超时 → unknown** | 抛 `/请求超时/` 且 `doesNotMatch(/malformed/)`；记录 `state==='unknown'`（不是 sending、不是 accepted）；请求 URL 是 `/api/session/prompt` |

四个用例都套了 `withDeadline(…, 2000)`：**将来若有人把修复改回去，是一条清晰失败而不是挂起整条 CI 链**。这个设计来自修前的真实现象（见 §2.4）。
